# خارطة طريق تشخيصية — linux-flow

## السياق

وثيقة تتبّع لمراجعة فنية شاملة للمشروع: تشخيص دقيق لأماكن الضعف الحقيقية في
الأداء والمتانة والديون التقنية والأمان وتغطية الاختبارات، مرتّبة كخارطة طريق
قابلة للتنفيذ.

**نطاق الوثيقة:**
- خارطة طريق تشخيصية — كل بند يُنفَّذ كمهمة مستقلّة + PR منفصل (التزاماً بقاعدة
  «مهمة واحدة لكل جلسة»).
- الترتيب حسب الأولوية: المتانة أولاً، ثم الاختبارات، ثم الأداء، ثم التنظيف، ثم الأمان.

**خلاصة الحالة:** البنية المعمارية للمشروع **سليمة وقوية** — فصل نظيف بين
`shared/`/`app/`/`daemon/`، لا تبعيات دائرية، `daemon` وحده يلمس `/dev/uinput`،
`thiserror` في كل crate، `ucred` مُطبّق، `zeroize` واسع الانتشار، وصفر persistence.
المشاكل ليست في الأساس بل في **الحواف**: نقاط backpressure، تنظيف موارد عند
الإلغاء، تسلسل cold-start، تغطية اختبارات ناقصة، وملفات تجاوزت حد الـ 150 سطر.

> **مبدآن حاكمان من DESIGN.md و ARCHITECTURE.md (لا يُكسَران):**
> - **التصميم batch متعمّد:** DESIGN.md §Pipeline(4–5) ينصّ على «**full utterance**
>   → OpenRouter» مع معالجة false-starts/self-corrections/reflow — وكلها تتطلب رؤية
>   الجملة كاملة. الحقن التدفّقي (streaming injection) يكسر دلالة المنتج، لذا **مستبعَد**.
> - **الخروج عبر `process::exit` قرار واعٍ:** ARCHITECTURE.md يوثّقه — مهام
>   `spawn_blocking` للاختصار غير قابلة للإلغاء بسهولة، والخروج المباشر يحرّر الـ flock
>   فوراً ويمنع فشل التشغيل اللاحق بصمت. لا يُعاد فتحه إلا كتحسين أناقة اختياري (B1).
>
> **ملاحظة على دقّة التشخيص:** الـ timeouts الكبيرة (LLM 20s، IPC 5s، Wayland portal
> ~25s) هي **سقوف أمان موثّقة** وليست latency فعلياً في الحالة العادية — لا تُعامَل كبطء.

## المحور الأول: المتانة

### M2 — `blocking_send` داخل PipeWire callback 🟠
- **الحالة:** ✅ محلول — PR #48. استُبدل `blocking_send` بـ `try_send` مع إسقاط آمن عند الامتلاء (تحذير مرة/جلسة) وإنهاء الـ mainloop عند إغلاق المستهلك.
- **الموقع:** `app/src/audio.rs`.
- **المشكلة:** الـ callback المتزامن لـ PipeWire يستدعي `tx.blocking_send(...)`. إذا امتلأ الـ channel وتأخّر المستهلك (tokio منشغل)، الـ callback يُحجَب — وقد يجوّع mainloop الصوت.
- **الأثر:** احتمال تقطّع/تأخّر في التقاط الصوت تحت الضغط؛ في أسوأ الحالات حجب الـ audio thread.

### M3 — تنظيف موارد ASR عند الإلغاء غير كامل 🟡
- **الحالة:** ⬜ مفتوح
- **الموقع:** `app/src/asr.rs`.
- **المشكلة:** عند الـ timeout/الخطأ يُستدعى `read_task.abort()` لكن WebSocket لا يُغلَق صراحةً (لا close frame). الموارد على جانب الخادم قد تبقى عالقة لحظياً.
- **الأثر:** منخفض — تسريب مؤقت لاتصال؛ لا يؤثر على المستخدم مباشرة.
- **اتجاه الإصلاح:** إرسال close frame صريح قبل الإلغاء حيثما أمكن.
- **الحجم:** PR صغير.

### M4 — `h.join()` لخيط الصوت يُتجاهَل ناتجه 🟡
- **الحالة:** ⬜ مفتوح
- **الموقع:** `app/src/audio.rs`.
- **المشكلة:** لو خيط الالتقاط panic، فشل الـ join يُبتلَع بصمت دون تسجيل.
- **الأثر:** منخفض — يُخفي أعطالاً صامتة في الصوت تصعّب التشخيص.
- **اتجاه الإصلاح:** فحص ناتج الـ join وتسجيل تحذير عند الـ panic.
- **الحجم:** PR صغير جداً.

### M5 — Mutex حقن `/dev/uinput` بلا حماية من التسمّم 🟡
- **الحالة:** ⬜ مفتوح
- **الموقع:** `daemon/src/uinput.rs`.
- **المشكلة:** `inner.lock()` و`injector.lock()` قد يُحجبان أو يعودان بخطأ تسمّم (poison) دون استراتيجية تعافٍ واضحة.
- **الأثر:** منخفض — بعد panic في الحقن قد يدخل الـ daemon حالة متدهورة.
- **اتجاه الإصلاح:** سياسة واضحة للتعامل مع الـ poison (إعادة تهيئة الجهاز أو رفض صريح).
- **الحجم:** PR صغير.

## المحور الثالث: الأداء (latency محسوس)

> **مبدأ حاكم:** التصميم batch (الجملة الكاملة → LLM → حقن دفعة واحدة) **مقصود** ولا يُكسَر. تحسين الأداء يكون **داخل** هذا الإطار: قياس أولاً، ثم تقليل الزمن حتى آخر token وتسريع cold-start — لا تغيير دلالة المنتج.

### P0 — قياس قبل أي تحسين (instrumentation موجود) 🔴
- **الحالة:** ⬜ مفتوح
- **الموقع:** سجلّات `tracing` الجاهزة في `pipeline.rs` (`llm start/done`, `asr waiting/done`, `inject start/ok`) و`asr.rs` (`EOS sent`).
- **المشكلة:** «بطيء» غير مُثبَت بأرقام. غير معروف بعد أين يضيع الوقت فعلاً: ASR finalize؟ زمن استجابة الـ LLM؟ cold-start؟ refocus؟ — كلها شبكية/خارجية إلى حدٍّ كبير.
- **اتجاه العمل:** تشغيل `--debug` وقياس الفروق الزمنية الفعلية على المسار الحرج عبر عدة جلسات قبل اختيار أي تحسين. هذا **شرط مسبق** لـ P1/P2 — بدونه يكون التحسين بالحدس.
- **الحجم:** لا كود (أو إضافة طوابع زمنية دقيقة مؤقتة). جلسة تحليل.

### P1 — streaming لاستجابة الـ LLM لتقليل الزمن حتى اكتمال النص 🟠
- **الحالة:** ⬜ مفتوح (مشروط بإثبات P0)
- **الموقع:** `app/src/llm.rs` (نداء OpenRouter الحالي batch).
- **المشكلة:** النداء batch ينتظر اكتمال الـ response كاملاً قبل أن يُعاد للـ pipeline. مع streaming يصل النص أسرع (خاصة الردود الطويلة) دون كسر دلالة «إعادة الصياغة الكاملة» — الحقن يبقى **دفعة واحدة بعد اكتمال آخر token**، لكن الزمن حتى ذلك الـ token قد يقصر.
- **القيد:** المكسب غير مضمون مع موديل `flash-lite` السريع أصلاً والردود القصيرة. **يُنفَّذ فقط إذا أثبت P0 أن زمن الـ LLM هو الاختناق.** يتطلب قراءة توثيق OpenRouter الرسمي أولاً.
- **الحجم:** PR متوسط، مشروط بنتائج P0.

### P2 — تحميل المفاتيح تسلسلي بدل التوازي (cold-start) 🟠
- **الحالة:** ⬜ مفتوح
- **الموقع:** `app/src/pipeline.rs` + `app/src/secrets.rs`.
- **المشكلة:** `resolve_key("soniox")` ثم `resolve_key("openrouter")` تتمّان **تسلسلياً**، كل واحدة D-Bus roundtrip كامل عبر Secret Service (connect + unlock + search).
- **الأثر:** يضاعف زمن بدء الـ Pipeline؛ ويتكرّر فحص الـ keyring مرتين على مستوى التطبيق (`wizard_flow::setup_needs` ثم `Pipeline::new`).
- **اتجاه الإصلاح:** `tokio::join!` لتحميل المفتاحين بالتوازي؛ ومراجعة إمكانية مشاركة اتصال Secret Service واحد وتفادي الفحص المزدوج.
- **الحجم:** PR صغير-متوسط.

### P3 — `wait_for_display(30s)` على cold-start 🟡
- **الحالة:** ⬜ مفتوح
- **الموقع:** `app/src/main.rs`.
- **المشكلة:** على الـ autostart قد ينتظر التطبيق حتى 30s لجاهزية الـ display server.
- **الأثر:** بطء بدء عند الإقلاع فقط (ليس على المسار الحرج).
- **القيد المهم:** retries بوابة Wayland (~25s) **مقصودة وموثّقة** في ARCHITECTURE.md (§إشعار فشل الاختصار) — لا تُقصَّر باستهتار. الكشف المبكر عن غياب الـ portal والسقوط الفوري لـ X11/evdev (مهمّ لبيئات بلا GlobalShortcuts portal مثل COSMIC/Pop!_OS) تمّ جزئياً سابقاً. يبقى فقط مراجعة قيمة الـ 30s نفسها.
- **اتجاه الإصلاح:** مراجعة هل 30s مبرَّرة أم يمكن خفضها مع آلية إعادة محاولة قصيرة. **لا** تُمَسّ منطق retry البوابة.
- **الحجم:** PR صغير.

## بنود مُنجَزة خارج الكتالوج الأصلي

### D1 — فشل `cargo deny check` + اعتماد native-tls الزائد 🟠
- **الحالة:** ✅ محلول — PR #49.
- **السبب:** ترقية أداة `cargo-deny` لـ 0.19.4 رفضت `deny.toml` القديم، وبعد إصلاح الصيغة كشفت: (1) crates المشروع بلا حقل `license`؛ (2) تراخيص تبعيات غير مدرجة (`Unicode-3.0`/`CC0-1.0`/`CDLA-Permissive-2.0`/`Unlicense`)؛ (3) `reqwest` يجرّ `native-tls`→`openssl`→`tempfile` الممنوع.
